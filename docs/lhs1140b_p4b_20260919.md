## 1. The defect, confirmed on the tree

The manifest of `molecular_scalar_gj1132_kzz1e9/HeH9.7`'s solve generation
`g0004_20260919T103629Z_9b8394a3` carries

    "parent": {"generation_id": null, "source": null,
               "compatibility": "not recorded by the run that wrote this state"}

while the run record that generation names,
`runs/r20260919T102944Z_32822/run.json`, carries

    "seed": ".../molecular_scalar_gj1132_kzz1e9/HeH9.7/states/g0003_20260919T052326Z_ffa78b36 (given)"

The runner knew the seed and the manifest did not, because `run_case.sh`
passed the publisher `${FIRST_GENERATION:-}` alone: the generation an
internal continuation continued, which is empty for a first solve however it
was seeded. READ, `publish_state.py`: the publisher had no other way in, and
`write_reproduce.py` printed `pick_seed.py`'s line as prose that no reader
can compare with a manifest.

## 2. What is recorded now

The seed is resolved ONCE, by the runner, into
`runs/<run id>/seed_identity.json`, and the publisher and the record reader
are both handed that one file, so the manifest and `REPRODUCE.md` cannot
disagree: neither tool forms a reading of its own.

`run_case.sh` (in the block the fixtures source with
`RUN_CASE_POLICY_ONLY=1`):

- `seed_selection_note` says WHO chose it: the tier of `models/pick_seed.py`,
  read from the second field of the line the tool prints; `SEED=` where the
  caller named the state; `models/pick_seed.py --list` for attempt 2 and
  later of the seed walk, which take the next candidate of the ranked list
  and are not a named seed.
- `seed_transformation` names WHAT was done to it, in one place, as three
  different starting states: `as_is`, `mapped` (interpolated onto this case's
  cell centers by `src/utils/map_state_to_grid.py`) and `converted` (an
  atomic state made into a molecular one by the binary,
  `molecular_seed_from_atomic_state.f90`). The conversion is not an
  interpolation: it changes which species the state carries, and it is
  recorded with what it changed, the base partition extension `x2` and the
  primitive held invariant.
- `record_seed_identity` writes the record, from the directory the pair was
  READ from and BEFORE the mapping: what the mapper writes is a state of this
  grid and of no other run.

`publish_state.py` (`seed_identity`, `publication_seed`, schema
`exhale_seed_identity/1`, and a `seed` subcommand that writes one) resolves
that directory into an identity: the case it came from, the generation where
the directory is one, the md5 of both halves, and, where the directory
publishes no generation, the generation of that case carrying the same pair,
recorded as `generation_by_md5` and labeled state identity rather than the
identity of a run (the review's caution, section 6.2: several attempts can
write one pair).

The manifest field `seed` carries it, beside the warm restart policy of
MODELS.md section 9.6, and the parent follows from it:

| the run was started from | `parent.generation_id` | `seed.kind` |
|---|---|---|
| a generation of THIS case (tier 0, or `SEED=` naming one) | that generation | a published generation |
| a generation of another case | null, WITH the reason | a published generation, with its own case |
| a pair no generation was published for | null, with the reason | a file pair, no generation published for it |
| the generation this run had just published | that generation | internal continuation, holding `initial_seed_of_the_run` |
| nothing (`Load IC? False`) | null, with the reason | cold start, established |
| nothing the publisher could read | null, with the reason | not established, with the reason |

A foreign generation is NOT written into `parent`: the parent chain is the
chain this case's index resolves (`demote_refused_parent` and
`solve_ancestor` both follow it), and an id that index cannot name is not in
it. The identity of such a seed is in `seed`, with its case, its generation
and its md5 pair.

`write_reproduce.py` prints the same record under
"### The seed identity, as the manifest records it", from the same file.

## 6. Noticed outside the item, and fixed

`tests/termination_classification.sh` check T7 failed intermittently
(MEASURED: 1 failure in 2 consecutive runs before the fix, 0 in 5 after).
The fixture touched its pass mark and then wrote the state, so on a
filesystem storing whole seconds the state was not `find -newer` than the
mark and a state the pass had written read as `stale_state`. The fixture now
sets the mark 60 seconds into the past. This is a defect of the fixture and
not of `classify_ending`: a solve takes longer than a second and never stands
in that gap, while this fixture writes its states in milliseconds.
