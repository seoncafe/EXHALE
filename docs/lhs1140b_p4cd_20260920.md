## 0. One correction to the item as written

P4b's memo and this item's brief both say that `run_closure.sh` publishes the
flux-closure rungs through the same publisher and hands it no seed. READ, the
delivered text of `LHS1140b/models/run_closure.sh` and of
`src/utils/element_flux_closure.py`: **neither publishes anything**. Neither
file names `publish_state.py` at all, and the 46 rung indexes of the catalog
were all written by `models/import_legacy_states.py`. The rungs would
therefore not have recorded `established: false`; they would have gone on
publishing nothing at all, and a rung's state would have been whatever
`k<NN>/output/` happened to hold.

So this item gives the closure runner BOTH halves at once: it publishes each
rung through the one publisher, and it resolves the seed of each rung first.

## 1. P4b-2, the seed of a flux-closure rung

Contract in `MODELS.md` section 9.13. A rung `k<NN>/` is a state directory
(section 9.1) and a ladder is a chain, so the seed of iteration 0 is the state
`run_closure.sh` mapped onto the current cell centers, and the seed of every
iteration after it is the iterate before it.

After the closure driver returns, `publish_rungs` walks the rungs in the order
the ladder ran them and, for each one whose bytes are not already published:

- resolves the seed ONCE into `k<NN>/runs/<run id>/seed_identity.json`,
  through `publish_state.py seed`, the same `exhale_seed_identity/1` record
  the catalog runner writes;
- names WHO chose it with `seed_selection_note` and WHAT was done to it with
  `seed_transformation`, both sourced from the policy block of
  `models/run_case.sh` (`RUN_CASE_POLICY_ONLY=1`) rather than restated, so
  the two runners cannot drift;
- classifies the ending with `classify_ending` of that same block, reads the
  phase from the binary's own `Restart intent:` echo through
  `import_legacy_states.phase_of`, and publishes with all of it.

The transformation is read from what the driver left: a rung carrying a
`seed.log` was mapped again (the driver carries the moved elemental reservoir
onto the iterate, and the moved R0 where it left a
`target_grid_Hydro_ioniz.txt`), and a rung with none was copied as it stands.
These are two different starting states and are recorded as two.

The rung before is a state directory of its own, so its generation is not in
the chain this rung's index resolves: `parent` stays null and says why, and
the identity is in `seed` with its case, its generation and the md5 of both
halves, by the rule of section 9.12.

The publication is idempotent. `rung_already_published` refuses a rung whose
index already names a generation holding exactly these two halves, so a
resumed or re-run ladder adds a generation only where the bytes are new.
Where `run_case.sh` cannot be read no rung is published and the runner says
so: an unclassified publication is what item P4a removed.

**Tests.** `models/tests/closure_seed_provenance.sh`, 22 checks, no binary and
no closure driver run: the runner is sourced with
`RUN_CLOSURE_PUBLISH_ONLY=1`, which defines the publication and runs nothing,
and the tools it exercises are copied into the work directory, so nothing is
written under the catalog.

## 2. P4c, the provenance recovered without rewriting anything

Contract in `MODELS.md` section 9.14. `models/recover_provenance.py` reads
the tree and writes, BESIDE each generation and never inside it,

    <state directory>/provenance/<generation_id>/provenance_recovered.json

with what was recovered, the file it was read from, that file's md5 and byte
count, the rule, the date and one of three confidences. Nothing is deleted:
a later recovery that says something different writes
`provenance_recovered_v2.json` beside the first and names what it supersedes,
and a recovery that says the same writes nothing.

**The rules, first that applies.**

1. The manifest's own `parent`: the parent of this case's chain IS the state
   the pass was started from. `established`, and the attachment states that
   this is RECORDED and not recovered.
2. A run record of the directory whose `solve_generation`,
   `solve_generations` or `evaluate_generation` names this generation and
   whose `seed` is not empty. One such record: `established`. Several with
   different seeds: `not established`, with every candidate kept.
3. A `REPRODUCE.md` of the case whose run window holds the moment the state
   was written (the `run=` stamp in the state's own header). Exactly one:
   `inferred from a single match`, and the attachment says that a window is
   not a name. Several: `not established`, with every candidate kept.
4. Nothing: `not established`, with the reason.

**A reader may use a recovered fact only where it is `established`, and says
it is recovered.** `publish_state.recovered_provenance` is the one entry and
returns nothing for a weaker confidence unless the caller is reporting ON the
recovery. `status.py` prints such a seed as `recovered: ...` in MODELS.md
section 8 (or `recorded in the manifest: ...` where the attachment restates
the manifest's own parent), and where the attachment is weaker it names the
attachment instead of stating a seed. `pick_seed.py --seed-provenance`
appends to each candidate what that state was itself started from, marked
`recorded:` or `recovered (...)`; without the option its lines are unchanged,
which is why no existing caller or fixture moves.

**MEASURED 2026-09-20 over the whole catalog**, read only, 398 published
generations in 137 state directories, and NOTHING WAS REWRITTEN:

| confidence | generations | of which |
|---|---|---|
| established | 176 | 172 the manifest's own parent, 4 a run record naming the generation |
| inferred from a single match | 10 | a `REPRODUCE.md` window |
| not established | 212 | no evidence anywhere in the tree |

Every one of the 398 gained an attachment, and 226 of them are the null-parent
population P4b measured: 4 + 10 + 212 = 226.

**This recovers more than P4b's count said it would**, by two rules P4b did
not apply. P4b found ONE generation whose seed a run record carries, the one
whose manifest names a `run_id`; there are FOUR, because a run record names
the generations it published whether or not the manifest names the run.
P4b found FIVE in a `REPRODUCE.md`; there are TEN, because a case keeps the
records it superseded in `runs/<run id>/superseded_case_products/` and those
speak for their own runs. The ten stay `inferred from a single match` and no
reader uses them.

## 3. P4d (i), the record bound to its log

A record that names a case-level log is bound to a path the next run of that
directory reuses. Two things are now done about it.

**At publication, the record is bound to the log BYTES.**
`publish_state.certification_from_log` records `source_md5` and
`source_bytes` of the log it read the block from, and the `ending` records
the md5 of the file `--ending-source` names. The generation already carried
the block itself in `certification.txt`, so a later reader can say whether the
file at that path is still the one the record was made from.

**For the records already published, every attachment states the binding it
finds.** The test is whether the file at the path the record names still
carries, verbatim, the block the generation holds.

The two `pre_D9s3/` copies were NOT rewritten, and that is the decision:
they are archival copies of cases as they stood before the D9 step 3 refresh,
and a rewritten copy of a record is a record of nothing. Their `NOTE.md`
